《雷隙 THUNDERGAP》技术方案

本文是 PRD v0.1 的技术配套文档：完整描述 M0 原型的实现方案（渲染、程序化生成、GPU 雨幕、 自研物理、程序化音频、DOM 后期），盘点性能预算与技术债， 并给出 M1–M4 各阶段的关键技术选型与演进路线。文中数值均以 index.html 当前代码为准。

01方案概述

技术目标

技术方案服务于 PRD 第 04 节的指标，可归纳为四条：

  • 零门槛进入：双击 index.html 即可游玩，无构建、无服务器、无网络请求（three.js 已本地化），首屏可玩 < 3 秒。
  • 氛围可承载：14000 条雨丝 + 动态闪电 + 指数雾在 1080p 中端 GPU 上稳定 ≥ 55 fps，支撑「一发脉冲点亮全城」的核心画面。
  • 机制可调：落雷频率、穹顶曲线、共鸣经济等全部收敛为可查表的数值，平衡测试不改结构。
  • 可演进：M1–M4 的模块化拆分、真实反射、自适应降级、移动端适配都有明确挂点，不需要推翻原型。

硬约束

分发形态
静态文件目录（index.html + js/three.min.js），无构建步骤，file:// 协议可直接运行
外部依赖
仅 three.js 一个本地文件，锁定版本；无字体、音频、贴图等任何外部资产
音频
WebAudio 全程序化合成，音频资产为零
贴图
窗格 / 假阴影为运行时 Canvas 生成，纹理资产为零
物理
自研圆柱 vs AABB 推出，不引入第三方物理引擎
目标平台
桌面浏览器（Chrome / Edge / Firefox / Safari），WebGL；移动端为 M3 目标

技术原则

  • CPU 让位 GPU。凡是「大量、重复、有规律」的运动（雨丝下落、涟漪扩散）全部放进顶点着色器或 InstancedMesh，主循环只更新 uniform。
  • 程序化优先于资产。城市、窗格、闪电折线、雷声、涟漪全部运行时生成——零资产换来零加载与无限随机布局。
  • 后期走 DOM，不走后处理管线。闪白、受伤红晕、暗角、镜头水痕全部是 CSS 叠加层（mix-blend-mode: screen + 渐变），省掉整套 EffectComposer 的成本与复杂度。
  • 数值即代码即文档。所有可调参数集中在常量与 state，与 PRD 第 07 节数值表一一对应。

主循环时序

dt = min(0.05, getDelta)→ 穹顶进度推进→ 玩家 / 碎片 / 目标→ HUD→ 闪电 & 落雷定时器→ 相机→ 特效→ render

开始前（title 界面）与结束后（结算卡）只运行「相机 + 特效 + 渲染」，玩法更新整体短路—— 菜单背景就是活的雨夜城市，这是「氛围先行」在架构上的体现。 dt 钳制在 50ms，防止后台切回标签页时的一帧大步长穿透楼体或跳过预警。

代码组织演进决策

M0 的单文件形态是有意为之：零构建约束下 file:// 协议无法使用 ES Modules（CORS 限制）， 打包器又会杀死「双击即玩」。M1 起拆分为多个 <script> 顺序加载的命名空间模块 （详见第 13 节选型 D1），拆分边界即上图的六层。

天空穹顶（自定义着色器）

半径 500 的反面球体，片元着色器按高度做三段色带插值（地平线紫 → 中层蓝 → 顶部近黑）， 并叠加 uFlash 闪电提亮项（高处增亮更多，模拟云层反射）。球体每帧跟随相机，天空永远「够远」。

// 片元核心：h 为归一化高度，uFlash ∈ [0, 0.5]
vec3 c = mix(uHorizon, uMid, smoothstep(0.42, 0.62, h));
c     = mix(c, uTop,  smoothstep(0.60, 0.95, h));
c    += uFlash * vec3(0.55, 0.68, 0.85) * (0.35 + 0.65 * h);

04程序化世界生成

城市生成算法（buildCity）

  • 网格步进：以 24m 步长在 ±95m（CITY/2）范围内双重循环，每个格点尝试生成一栋楼。
  • 跳过规则：① 中央 36×36m 留给广播塔广场；② 四角 26m 内留白（防止边角死区）；③ 16% 概率空地——空地是玩家实际的可通行捷径，不是浪费。
  • 楼体参数分布：宽/深 9–15m 均匀分布；高 10 + pow(rand, 1.7) × 58 ——幂律让矮楼多、高楼少，天际线自然；位置抖动 ±1.5m 打破网格感。
  • 碰撞盒同步：生成楼体的同时向 boxes[] 推入 AABB {minX, maxX, minZ, maxZ, h}，物理与渲染天然一致，无需后期从 Mesh 反推。
  • 屋顶警示灯：h > 40m 的楼以 70% 概率挂红色闪灯（相位随机），兼作高空地标。

窗格纹理（运行时 Canvas）

64×128 的 Canvas 上以 13×11px 步进画窗，每扇 42% 概率点亮，点亮色在三档色温（暖橙 / 暖白 / 冷白）中随机； 作为 emissiveMap 而非 diffuseMap 使用，RepeatWrapping 按楼体尺寸平铺。 一张贴图服务全城楼体（材质共享），纹理内存几乎为零。

六面 UV 适配（scaleBoxUV）

BoxGeometry 的 24 个顶点按 +X/−X/+Y/−Y/+Z/−Z 六面分组，侧面 UV 按 尺寸/3.2m × 高/3.4m 设置重复次数， 保证窗格在世界空间中始终是约 3m 一层的等大格子；顶/底两面 UV 归零，屋顶不显示窗格。

广播塔（终点）

组合体：4 根微倾圆柱塔腿 + 7 道环 + 桅杆 + 红色信标 + 130m 高的加法混合导航光柱（opacity 0.09， 全城任意角度可见的终点地标）+ 塔基平台与闸门。塔基同时向 boxes[] 推入碰撞盒（不可穿越， 胜利判定走距离 9.2m 触发而非穿入）。

碎片布点与 freeSpot 重定位

8 片碎片有 8 个手工预设锚点（保证相对塔的方位分布），但锚点可能落在随机生成的楼体内部， 因此用 向日葵螺旋（黄金角 2.399 rad，步进 1.7m，最多 60 次尝试）向外搜索第一个 「不与任何碰撞盒相交（留 2.4m 余量）、不在广场、不出城」的落点。 该函数同样可用于未来任何「必须生成在可通行区」的对象。

已知缺口 · 随机数不可复现

当前全部使用 Math.random()，同一布局无法复现——玩家报了一个「卡进楼里」的问题时无法重建现场， 埋点也无法关联具体布局。M1 改为可播种 PRNG（mulberry32 一类的 15 行实现）， seed 写入 run_end 埋点与结算卡，作为「本局编号」。

05GPU 雨幕与涟漪

雨幕：位置完全在顶点着色器计算（FR-02）

14000 条雨丝 = 28000 个顶点的 LineSegments。CPU 在初始化后每帧只写 3 个 uniform（uTime / uCam / uBright）， 位置、循环、风偏移、相机跟随全部在 GPU 完成：

数据布局
属性布局含义
aSeedvec3 × 2 顶点雨滴初始种子（同一雨丝的两个端点共享，是全部随机性的来源）
aSpeedfloat × 2下落速度 17–30 m/s
aEndfloat × 20 = 雨滴头，1 = 拖尾端
顶点着色器核心
// 1. 循环下落：mod 让雨滴永远落在 [0, 46m] 窗口内
float fall = mod(aSeed.y - uTime * aSpeed, uHeight);
p.y = fall;
// 2. 风偏移：越接近地面偏得越多（(高度-当前位置)×系数）
p.x += uWind.x * (uHeight - fall) * 0.06;
p.z += uWind.y * (uHeight - fall) * 0.06;
// 3. 拖尾：尾端点向下偏移，长度与速度成正比（快雨长尾）
p.y -= aEnd * (0.55 + aSpeed * 0.035);
// 4. 相机跟随：对「相对相机的偏移」取 mod，雨幕无限平铺在世界中
vec3 rel = p - uCam;
rel.x = mod(rel.x + uArea * 0.5, uArea) - uArea * 0.5;
rel.z = mod(rel.z + uArea * 0.5, uArea) - uArea * 0.5;

关键点是第 4 步：雨的种子位置是固定的，移动的只是 110×110m 的取景窗口—— 相机走到哪，窗口就 wrap 到哪，14000 条雨永远「够用」，不需要粒子重生逻辑。 frustumCulled = false 关闭视锥剔除（雨包围球永远覆盖相机，剔除只会带来闪烁）。

联动
  • 闪电联动：uBright 冲到 1.0 后按 1.6/s 回落到基线（0.32 + 穹顶进度 × 0.25）——雨丝颜色与透明度整体提亮，雨幕在闪电瞬间「显形」。
  • 穹顶联动：基线亮度与雨声音量随穹顶进度同步上升，视觉与听觉共享同一条曲线。

涟漪：InstancedMesh + 每帧 CPU 矩阵（340 实例）

单几何体（RingGeometry 0.10–0.17）实例化 340 份，涟漪在相机周围 70m 内随机重生， 生命期 0.45–1.15s，缩放 0.4 → 2.8、透明度随寿命衰减，instanceColor 控制青色调与穹顶强度。 这是全场景唯一每帧写 instanceMatrix 的系统，成本约 340 次 4×4 矩阵写入，实测可忽略， 但它是第 12 节「降级档位」的 first cut 对象。

06闪电与落雷系统

系统刻意分为两类：环境闪电是舞台灯光与免费视野（PRD FR-04），威胁落雷才是敌人（FR-11）。 两者共用折线生成器，语义完全不同。

折线闪电生成（makeBoltPath / spawnBolt）

两端点间线性插值 14 段，中间点叠加随机抖动（主脉 jitter，支线 ×1.5）； 用两条叠加的 Line（副线透明度 0.5、路径不同）模拟辉光粗细——不引入宽线扩展或 Billboard， 0.23s 生命周期内肉眼足够。闪电死亡时逐个 dispose geometry/material，防止长局内存增长。

落雷状态机

spawn：预警环 + 内圈→ WARN 1.35s：环呼吸脉动→ detonate：闪电柱 + 伤害/击退 + 冲击波→ FADE 1.4s：环淡出 → 回收

伤害结算要点

  • 距离用 2D 平面距离（hypot），忽略高度差——跳起不躲雷，避免「跳跃无敌」漏洞。
  • 无敌帧（0.9s）在结算入口检查，多连发雷最多吃一发，对应 PRD「防止瞬间秒杀」的数值约束。
  • 击退向量 = 玩家相对落点的单位方向 × 9，附加竖直 5.2 的抛起——击退同时是「把玩家推出预警环」的纠错机制。

07回声脉冲与收集（FR-08 / FR-09）

脉冲的视觉三件套

元素方案
地面扩散环RingGeometry 加法混合，42 m/s 匀速扩散至 34m，透明度线性衰减
半球扩散壳半透 wireframe 半球，0.9× 半径同步膨胀——给「声呐」以体积感

「照亮」的判定模型

脉冲不是灯光渐变，而是一个移动的球形波前：每帧检查所有未拾取碎片， 满足 |dist(碎片, 玩家) − 波前半径| < 4.5m 即判定「被波前扫过」，碎片显形计时器置 5s。 这是一个 O(碎片数) 的纯数学判定，与「光锥照射」相比无需射线检测，且语义更接近声呐（隔墙也能感知）。

碎片显形与拾取

  • 双通道显形：被脉冲扫过（lit 5s）或玩家进入 14m 常显半径——近处碎片不会因为没脉冲而隐形。
  • 显形渐变：核心/线框笼/指引光柱/点光四个属性用同一帧率无关的 lerp（dt×5）趋近目标值，显形与熄灭都无跳变。
  • 拾取：水平距离 2.4m 判定（试玩轮由 3D 1.7m 放宽）→ 计数 +10% 穹顶回退 +6 HP → 播放拾取音 + 无线电底噪 → 字幕推进叙事（八段固定顺序）。

共鸣经济

上限 100→ 脉冲 −25→ 回复 7.5/s（3.3s 回满一次）→ 满值 4 连发↺

不足 25 时脉冲被拒绝并给出字幕提示（「共鸣值不足——等它回满」），机制数值全部集中在 state.resonance 一处，平衡调优只动三个常量。

移动积分

速度不直接赋值，而是向目标速度做帧率无关的指数趋近（系数 dt×9）——自带惯性起停， 也是击退冲量能自然衰减回行走状态的原因。竖直方向独立积分（重力 → 位置 → 地面钳制）。

碰撞：圆柱 vs AABB 最小穿透轴推出（collide）

// 对每个碰撞盒：先 AABB 相交粗测（圆近似为方），再取四个方向穿透深度的最小值推出
dl = (p.x + r) - b.minX;  dr = b.maxX - (p.x - r);
db = (p.z + r) - b.minZ;  dt = b.maxZ - (p.z - r);
m  = min(dl, dr, db, dt);   // 沿最小穿透轴位移，相当于滑墙

推论与已知边界：

  • 逐盒顺序求解天然支持「滑墙」手感（贴墙移动不被卡死）；但凸凸重叠的楼间缝隙可能产生推挤抖动——当前布局楼间距 ≥ 9m，实际不会触发。
  • 圆近似为方（AABB 膨胀），转角碰撞比真圆略「方」——对 0.5m 半径的第三人称视角不可感，不值得换圆 vs AABB 的三角函数解。
  • 只解水平面，竖直方向只有地面一个平面——楼顶不可站（PRD 明确楼体实心不可攀爬，这是约束不是缺陷）。

程序化角色动画

无骨骼、无动画文件。runPhase 以 dt × (3.2 + speed×1.5) 累进（速度越快步频越高）， 腿臂反相正弦摆动（臂幅 ×0.8）、身体 bob、围巾随速度后飘并叠加慢速正弦、裙摆 z 向摆动。 全部是一阶正弦函数，但叠加之后「雨夜奔跑」的节奏感成立；受击/拾取/结局等状态动画缺口见第 13 节选型 D3。

相机（FR-06）

  • 球坐标跟随：目标点 = 玩家 +1.55m，半径 7.2m，yaw/pitch 定位后 lerp（dt×7）平滑追踪。
  • 避障：从目标点向期望机位做 Raycaster 检测（仅楼体层），命中则拉近距离（−0.7m 余量，下限 1.6m）——镜头永不穿楼。
  • 震屏：camShake 衰减量（dt×2.4）控制三轴随机偏移（±shake×0.55），落雷引爆时置 0.85。
  • 下限钳制：相机高度 < 0.9m 时抬起，防止贴地翻转为地下视角。

浏览器自动播放策略

AudioContext 必须在用户手势后创建/恢复。initAudio() 挂在「进入雨夜」按钮点击上， 创建后立即检查 ctx.state === 'suspended' 并 resume。音频未就绪时全部播放函数静默返回， 游戏逻辑不依赖音频可用性。

为什么坚持程序化音频

① 零资产 = 零加载，首屏可玩指标不受伤；② 雷声延迟/音量与游戏内距离是同一套数值，视听同步天然成立； ③ 包体无限接近 0，对「发一个链接就能玩」的传播形态友好。代价是音色天花板低（无真实采样质感）， 若 M2 后需要更高质感，可对「雨幕底噪」单独引入采样文件，其余保留合成。

罗盘数学

把「塔 − 玩家」方向向量投影到玩家视角的前/右坐标系： fwd = −vx·sin(yaw) − vz·cos(yaw)，right = vx·cos(yaw) − vz·sin(yaw)， 指针角度 = atan2(right, fwd)。罗盘永远以「玩家朝向」为上，距离取 2D 平面距离。

字幕系统

单行容器 + innerHTML（支持 <b> 强调色），say(text, dur) 用单 timer 覆盖式更新—— 新字幕顶掉旧字幕，无队列。M1 分阶段引导（FR-15）需要字幕队列与触发条件系统，挂点已留好。

胜负判定

  • 胜利：集齐 8 片 且 距塔水平距离 < 9.2m（塔基碰撞盒外沿触发，无需寻找「门」）。

13演进路线（M1–M4 关键技术选型）

与 PRD 第 12 节里程碑对齐，列出每个技术决策的候选方案与取舍。

D1 · 代码模块化（M1，前置 TD-5）

方案取舍
A. ES Modules + 构建步骤工程体验最好，但引入 node 工具链，杀死「双击 index.html 即玩」——违背核心分发约束。否决。
B. ES Modules + Import Map无构建，但 file:// 下被 CORS 拦截，必须起本地服务器，玩家侧不可用。否决。
C. 多 script 命名空间（选定）按第 02 节六层拆为 6–8 个文件，挂 window.TG 命名空间，index.html 按依赖顺序引入。保留 file:// 直开与零构建；代价是无静态检查（用 JSDoc 注释 + 编辑器推断弥补）。M1 执行。

D2 · 积水真实反射（FR-03，M1–M2）

方案取舍
A. 全城 Planar Reflector效果最真，但整地面一次额外场景渲染，帧预算翻倍风险。否决。
B. SSR 屏幕空间反射需后处理管线，与「后期走 DOM」原则冲突，移动端不可行。否决。
C. 局部镜像 + 翻转网格（选定）仅塔前主广场放一块 512² RenderTarget 的 Planar Reflector（只渲染楼体层）；外围积水保留现有高光近似。风格化「假反射」（翻转楼体 + 渐隐遮罩）作为 B 计划。预算内效果收益最大化。

D3 · 角色状态动画（FR-07，M1）

原则：不引入骨骼动画资产管线（维持零资产），受击/跌倒/拾取/结局姿态用「目标姿态 + 姿态混合」实现—— 为现有程序化摆动定义目标 pose（蜷缩/踉跄/举手），按事件触发 lerp 进出。若 M2 后表现力不足，再评估 glTF 骨骼角色， 届时模块化（D1）已完成，替换面收敛在 buildPlayer/updatePlayer 内。

D4 · 性能自适应降级（FR-19，M2）

  • 采样：每帧累计 rAF 间隔，2s 输出一次滑动平均 fps 入 perf_sample 埋点。
  • 三档位：高（现状：雨 14000 / pixelRatio 1.85 / 涟漪 340）；中（8000 / 1.25 / 200）；低（4000 / 1.0 / 120 + 关 MSAA）。
  • 切换规则：连续两拍 < 45fps 降一档，连续两拍 > 58fps 升一档（防抖动，单向滞后），10s 冷却。
  • 重建成本：雨丝数变更需重建 BufferGeometry（一次性 ~10ms 卡顿，切档时用闪电白帧掩护）。
  • 设置面板（FR-20）暴露画质档位覆盖自动策略。

D5 · 空间化音频（FR-18，M1）

WebAudio 原生 PannerNode（HRTF）挂到落雷预警环、碎片嗡鸣、雷声三个声源；AudioListener 每帧同步相机位姿。 纯节点操作，无资产引入，直接强化「听声辨位」的核心体验。风险：Safari HRTF 历史兼容性问题，验收矩阵单独列（第 14 节）。

D6 · 移动端触控（FR-21，M3）

虚拟摇杆（左）+ 拖屏视角（右）+ 脉冲大按钮；雨丝减半、涟漪减半、pixelRatio 1.0、关 MSAA 为移动档基准； Pointer Lock 相关代码路径全部特性检测（'ontouchstart' in window 分流）。 需要真实设备矩阵测试，进入 M3 前先出技术预研 spike。

D7 · 埋点与本地化（M2）

  • 埋点：按 PRD 第 11 节七事件实现 TG.telemetry(event, fields)；事件先写 localStorage 环形缓冲（离线可用），存在配置的上报端点时批量 POST；设置面板提供「匿名数据」开关（默认开）。
  • 本地化：抽离 fragLines、字幕、HUD、结局卡文案为 i18n 字典（简中为基准键），M3 增补繁中/英/日；程序化音频不受影响。
